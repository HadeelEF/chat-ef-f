# ADR-0023 — سجل نشر `dev` على #15، و`CURRENT_STATE.md` عند تغيّر الحالة المتحققة فقط

| Field | Value |
|---|---|
| Status | Accepted — قرار المالك (2026-10-26، #235) |
| Date | 2026-10-26 |
| Deciders | مالك المشروع (@faenazi) — موافقة صريحة في جلسة Claude Code Cloud |
| Related | يعدّل ADR-0009 البند 3؛ ADR-0010، ADR-0011؛ #15، #234، #235 |

## Context

- ADR-0009 البند 3: «كل دمج أو `apply` أو نشر يُسجّل بأدلته على الـ Issue المتتبع وفي `project/CURRENT_STATE.md`».
- مع النشر التلقائي (ADR-0010) صار كل دمج يمس الواجهة يحتاج PR ثانياً بعنوان «docs: state — … deployed» لكتابة معرّف النشر.
  عُدّل الملف 27 مرة في أسبوع.
- الملف وصل إلى 10,239 بايت من حد 10,240 (`repo_checks.py budgets`)، فصار كل تحديث يتطلب حذف حقيقة أخرى.
- صفوف §1 تراكمت فيها أعداد الاختبارات ومعرّفات النشر الموجودة أصلاً في وثائق الاختبار والـ Issues، خلافاً لقاعدة
  «حقيقة واحدة في وثيقة واحدة» (AGENTS.md).
- اقترح الوكيل أربعة تغييرات (نسخة تاريخية، وسطر لكل مجال، وقائمة واحدة لفحوص المالك، وهذا القرار)، فردّ المالك:
  «نعم نفذ الأربعة كلها».

## Decision

1. **سجل النشر:** كل نشر لبيئة `dev` (تلقائي أو `config apply` أو `railway-deploy.sh`) يُسجَّل بتعليق واحد على
   [#15](https://github.com/faenazi/ef-ai-workspace/issues/15).
   - التعليق يحوي: commit على `main`، والـ PR، ومعرّف النشر لكل خدمة وحالته، وما فُحص في سجل البناء والإقلاع.
   - يكفي سطر يربط إليه على Issue الميزة.
2. **`project/CURRENT_STATE.md` يتغير فقط حين تتغير الحالة المتحققة.** أمثلة على ذلك:
   - قدرة جديدة تصل إلى Tested أو Verified، أو يتغير مستواها.
   - بند NOT RUN يُنفَّذ أو يُضاف.
   - عائق يُفتح أو يُغلق.
   - تتغير المهمة التالية.
   - نشر يفشل أو يكشف مشكلة.
3. **لا PR مستقل لتسجيل نشر ناجح.** حقل «آخر نشر» في الملف يشير إلى #15 بدل معرّف بعينه.
   - PR الميزة يحدّث صفّها بمستوى التحقق الذي حققه قبل الدمج.
   - سجل #15 هو دليل النشر؛ الوثيقة المدموجة ليست دليل نشر.
4. **فحوص المالك من الجوال** في قائمة واحدة ([#234](https://github.com/faenazi/ef-ai-workspace/issues/234))، يُشار إليها مرة واحدة من الملف.

باقي ADR-0009 دون تغيير: التفويض بالدمج والنشر على `dev`، وما يبقى بقرار المالك.

## Rationale

- معرّف النشر حقيقة تشغيلية تتغير مع كل دمج، ومكانها سجل زمني (#15)، لا لقطة الحالة.
- الملف يبقى مقروءاً من الجوال في دقيقة، وفيه متسع لما يتغير فعلاً.
- يختفي PR إضافي بعد كل ميزة دون أن يضيع دليل: كل نشر ما زال مسجلاً بأدلته.

## Alternatives considered

| البديل | لماذا لم يُختر |
|---|---|
| رفع حد الملف | يؤجل المشكلة أسبوعاً بالمعدل الحالي، ويُضعف قراءته من الجوال |
| إبقاء PR «deployed» مع اختصار الصفوف | يحل الحجم لا التكرار؛ يبقى PR إضافي لكل ميزة |
| تسجيل النشر في Issue الميزة فقط | يتفرّق السجل على عشرات الـ Issues؛ لا مكان واحد لآخر نشر |

## Consequences

- AGENTS.md (القاعدة 10: «each recorded on the tracking Issue») و`docs/operations/railway.md` («تُسجّل على #15») يوافقان القرار
  كما هما.
- `CURRENT_STATE.md` لا يحمل معرّفات نشر؛ من يريد آخر نشر يفتح #15.
- إن نُسي تعليق #15 بعد نشر فلا دليل على النشر؛ لذلك هو جزء من مسار الدمج في `implement-feature`.
