## Context

- منذ D2 المعدّل في #16 (2026-10-18) كان كل PR يتطلب **بوابة جودة يدوية** على SHA الرأس النهائي: `run-all.sh` كاملاً، والـ smoke
  وفحص الصور حسب التغيير، وجدول `PASS/FAIL/SKIP/NOT RUN` بإصدارات الأدوات في الـ PR و`CURRENT_STATE.md`.
- عملياً صار ذلك عائقاً إدارياً لمطوّر منفرد يعمل من الجوال مع وكيل: دُمجت PRs توثيقية (#61، #63) دون تشغيل البوابة، فأنشئت
  [#60](https://github.com/faenazi/ef-ai-workspace/issues/60) لاستكمالها بأثر رجعي، وتوقف التقدم نحو R0.2 على عمل ورقي لا يغيّر سلوك المنصة.
- قرار المالك (2026-10-19، نصاً من التعليمات): «During the current Development, Testing and Demo phases: No mandatory formal
  Quality Gates. No mandatory GitHub Actions. No mandatory full QA suite before every PR merge. [...] Formal release Quality
  Gates will be established and enforced before the platform enters Production».

## Decision

**خلال مراحل التطوير والاختبار والعرض (كل ما قبل الإنتاج):**

1. **لا بوابة جودة رسمية إلزامية لكل PR.** لا GitHub Actions إلزامية، ولا `run-all.sh` كاملاً إلزامياً قبل الدمج، ولا build أو
   Docker smoke أو فحص صور لتغييرات التوثيق فقط، ولا مراجعة معمارية/أمنية رسمية لكل PR عادي. لا يُمنع دمج تطويري عادي لمجرد
   أن `run-all.sh` لم يُشغَّل.
2. **تحقق المطوّر حسب حاجة المهمة** — نشاط هندسي وليس بوابة اعتماد:
   - **توثيق فقط:** مراجعة صحة المحتوى، وفحص الروابط/الصيغة المتأثرة حيث يتيسّر (مثلاً `repo_checks.py links`).
   - **وظيفة/سلوك:** بناء أو اختبار السلوك المتأثر حيث أمكن، وإصلاح العيوب المكتشفة، وتسجيل الدليل المفيد باختصار.
   - **بنية تحتية أو حساسة أمنياً** (مدخلات صور Railway المراقَبة، `railway.ts`، Compose، الأسرار، المصادقة، التعريض): فحص أثر
     النشر والأمن، وتشغيل الفحوصات ذات الصلة بحكمة (مثل `railway_checks.py`، `compose_checks.py`، smoke، gitleaks)، والحصول على
     أي تفويض أمني مطلوب. **لا يُدمج عن علم إعداد مكسور أو غير آمن.**
3. **مسار التطوير:** Issue → فرع مركّز → تنفيذ → تحقق مناسب → PR → مراجعة الفرق → squash merge → تحديث الـ Issue و
   `CURRENT_STATE.md` عند تغيّر الحالة المتحقق منها. يبقى الوكيل مفوَّضاً بالدمج وفق ADR-0009 بعد **مراجعة ذاتية للفرق وتحقق
   مناسب للمهمة** (بدلاً من «نجاح بوابة الجودة اليدوية»).
4. **الصدق في الأدلة لا يتغير:** لا يُوسم فحص لم يُشغَّل بأنه ناجح؛ يُذكر ما شُغّل فعلاً. لا يلزم جدول `NOT RUN` شامل لكل فحص
   غير ذي صلة، لكن أي ادعاء تحقق يحتاج دليلاً.
5. **الأدوات باقية:** `run-all.sh` والاختبارات السلبية والـ smoke وفحص الصور والـ workflows تبقى متاحة للتحقق الاختياري أثناء
   التطوير ولتأهيل الإنتاج لاحقاً؛ لا يُحذف أو يُعطّل أي منها.
6. **لا إطار متدرج جديد:** لا يُعتمد إطار Light/Standard/Full أو أي مرحلة QA إلزامية بديلة في التطوير.

**قبل الإنتاج (R1.0 / M6–M8):** تُعرَّف بوابات جودة رسمية وتُفرض قبل أي go-live — اختبارات وظيفية وتكامل وأمن وثغرات وإمكانية
وصول وأداء وتعافٍ من الكوارث وتحقق النشر، مع مراجعة مستقلة واعتمادات المالك والأمن. تتابعها
[#58](https://github.com/faenazi/ef-ai-workspace/issues/58) وبوابات R1.0؛ **لا يوجد اعتماد إنتاج الآن**.

**لا يتغير بهذا القرار:** حماية الأسرار، البيانات الاصطناعية فقط على Railway EU West، حظر بيانات الصندوق السرية، منع ربط Entra
الحقيقي، تفويض النطاقات والتعريض العام، الإنفاق، قرارات المخاطر الأمنية، شروط القبول المؤقت SC-18 (فحص الصور عند تغيير digest
وقبل أي تعريض عام)، واعتماد الإنتاج. بوابات الإصدارات R0.x تبقى **قرارات Go/No-Go للمالك على نتائج المنتج** بأدلة تشغيل مناسبة،
وليست بوابات QA رسمية.

## Rationale

السرعة والشفافية في مرحلة لا تحوي بيانات حقيقية ولا مستخدمين فعليين، مع إبقاء كل ما لا يُرجع بسهولة (الأسرار، البيانات، التعريض،
الإنفاق، الإنتاج) تحت ضوابطه. الاختبار يظل نشاطاً هندسياً يُمارس حيث يفيد، والبوابات الرسمية تُبنى مرة واحدة حين تكون ذات قيمة:
قبل الإنتاج.

## Alternatives considered

| البديل | سبب عدم الاختيار |
|---|---|
| إبقاء بوابة الجودة اليدوية لكل PR (D2 المعدّل) | رفضها المالك؛ أنتجت ديناً ورقياً (#60) دون تحسين سلوك المنصة |
| إطار متدرج Light/Standard/Full | رفضه المالك صراحة لهذه المرحلة؛ يعيد البيروقراطية بشكل آخر |
| إلغاء الاختبار كلياً | يسمح بدمج إعداد مكسور يُنشر تلقائياً إلى Railway `dev` (ADR-0010)؛ القرار يُبقي التحقق المناسب للمهمة |
| استعادة GitHub Actions كبوابة | قرار D2 المعدّل قائم (لا Actions)؛ ميزانية Actions غير متاحة (#10) |

## Consequences

- يعدّل ADR-0009 البند 1: الدمج بعد مراجعة ذاتية وتحقق مناسب للمهمة. باقي ADR-0009 (Railway `dev` فقط، ما يبقى للمالك) دون تغيير.
- يعدّل نتيجة ADR-0010: الضابط الوحيد قبل نشر مدخلات الصور المراقَبة هو **فهم الوكيل لأثر النشر وتحققه قبل الدمج**؛ لذلك أي تغيير
  في watched paths يُعامل كتغيير بنية تحتية (البند 2 أعلاه). حماية `main` (#3) تزداد أهمية.
- [#60](https://github.com/faenazi/ef-ai-workspace/issues/60) تُغلق **Not planned / Superseded**: نتائج `run-all.sh` على PR #61 و#63
  تبقى **NOT RUN** تاريخياً، ولا تتحول إلى PASS.
- السجل التاريخي محفوظ: استثناءات CI-EX-01..03 وبوابة D2 المعدّل تبقى مذكورة كتاريخ في [DoD](../../quality/definition-of-done.md).
- خطر متبقٍ مقبول: عيوب قد تُكتشف بعد الدمج بدلاً من قبله؛ يعوّضها التحقق المناسب للمهمة، وrevert سريع، وبيئة اصطناعية فقط.
- يمكن للمالك إعادة أي بوابة أو تضييق القرار في أي وقت؛ ينتهي القرار تلقائياً عند الانتقال إلى الإنتاج أو أي بيانات حقيقية.

## Verification

- الوثائق المتأثرة (DoD، testing-strategy، delivery-governance، AGENTS.md، CONTRIBUTING، قالب الـ PR، CURRENT_STATE، RELEASE_PLAN،
  README، CHANGELOG) محدّثة في نفس الـ PR، و`repo_checks.py` يتحقق من فهرسة هذا الـ ADR وأقسامه وروابطه.
- لا workflow أو سكربت أو فحص حُذف أو عُطّل (`git diff --stat` للـ PR يقتصر على Markdown).
