# تعريف الإنجاز (Definition of Done)

**السياسة الحالية ([ADR-0011](../architecture/adr/0011-production-only-quality-gates.md)، قرار المالك 2026-10-19):** في مراحل
التطوير والاختبار والعرض **لا توجد بوابة جودة رسمية إلزامية لكل PR**؛ التحقق نشاط هندسي حسب حاجة المهمة. بوابات الجودة الرسمية
تُعرَّف وتُفرض **قبل الإنتاج** (§2). الضوابط الأمنية وضوابط البيانات (§3) لا يُعفى منها في أي مرحلة.

## 1. مرحلة التطوير والاختبار والعرض (الحالية)

المسار: **Issue → فرع مركّز → تنفيذ → تحقق مناسب للمهمة → PR → مراجعة الفرق → squash merge → تحديث الـ Issue و`CURRENT_STATE.md`**.
التخطيط: إصدار المنتج (R0.x) → Epic → Issue. كل Issue تذكر الإصدار والنوع والأولوية (P0/P1/P2) والنتيجة وIn/Out وFR/NFR والاعتماديات
ومعايير قبول قابلة للاختبار والأدلة والتراجع؛ الـ Epic نية واعتماديات وبوابة خروج وقائمة Issues، لا PR ضخم. لا ملف backlog مكرر.

يُعتبر عنصر التنفيذ (Issue) **DONE** عندما:

1. معايير قبول الـ Issue متحققة، ولكل معيار دليل مختصر على ما فُحص فعلاً (أمر ونتيجته، لقطة، رابط).
2. التغيير مدموج عبر PR مركّز (squash). الوكيل يدمج PRs التطوير بعد **مراجعة ذاتية للفرق** وتحقق مناسب للمهمة
   ([ADR-0009](../architecture/adr/0009-development-phase-agent-delegation.md) كما عدّله ADR-0011). GitHub Actions **غير مطلوب**.
3. التوثيق المتأثر محدّث في نفس الـ PR، و[CURRENT_STATE.md](../../project/CURRENT_STATE.md) عند تغيّر الحالة المتحقق منها،
   و`CHANGELOG.md` للتغييرات الملحوظة أو الحوكمية، وADR عند قرار معماري.
4. لا عيب حرج معروف ناتج عن التغيير، ولا خرق للضوابط في §3.
5. الـ Issue محدّثة (رابط الـ PR وSHA الدمج) ومغلقة فقط إن تحققت معاييرها فعلاً.

### التحقق المناسب للمهمة (إرشاد هندسي، ليس بوابة)

| نوع التغيير | ما يُتوقع عملياً |
|---|---|
| توثيق فقط | مراجعة صحة المحتوى، وفحص الروابط/الصيغة المتأثرة حيث يتيسّر (`python3 scripts/validate/repo_checks.py links adr`). لا Docker ولا smoke ولا فحص صور |
| وظيفة/سلوك/اختبارات | بناء أو تشغيل السلوك المتأثر حيث أمكن (مثل `tests/integration/`)، وإصلاح العيوب المكتشفة قبل الدمج، وذكر ما شُغّل |
| بنية تحتية أو حساس أمنياً (مدخلات صور Railway المراقَبة، `railway.ts`، Compose، الأسرار، المصادقة، التعريض) | فهم أثر النشر التلقائي ([ADR-0010](../architecture/adr/0010-railway-dev-autodeploy-from-main.md)) والأثر الأمني، وتشغيل الفحوصات ذات الصلة (`railway_checks.py`، `compose_checks.py`، smoke، gitleaks…)، والحصول على أي تفويض مطلوب. لا يُدمج عن علم إعداد مكسور أو غير آمن |

`scripts/validate/run-all.sh` وكل الـ smoke وفحص الصور **أدوات متاحة** لهذا التحقق، وليست شرطاً إدارياً موحّداً لكل PR.
لا يُعتمد إطار متدرج (Light/Standard/Full) ولا مرحلة QA إلزامية بديلة في التطوير.

### الصدق في الأدلة (لم يتغير)

- لا يُوسم فحص لم يُشغَّل بأنه ناجح؛ يُذكر ما شُغّل فعلاً. لا يلزم سرد كل فحص غير ذي صلة، لكن كل ادعاء تحقق يحتاج دليلاً.
- **نجاح فحص التوثيق وحده لا يُثبت عمل وظيفة في المنتج.** الوثائق الموجودة ≠ وظيفة تعمل.
- مستويات الحالة المسموحة في التقارير: `Planned` → `Implemented` → `Configured` → `Tested` → `Verified` (في بيئة مستهدفة) → `Approved`.
- لا تُغلق مرحلة (Milestone) إلا بعد تحقق معايير قبولها في [ROADMAP.md](../../project/ROADMAP.md) مع أدلة.
- بوابات إصدارات المنتج R0.x قرارات **Go/No-Go للمالك على نتائج المنتج** بأدلة تشغيل مناسبة
  ([ROADMAP §3](../../project/ROADMAP.md))، وليست بوابات QA رسمية.

## مستويات أدلة التحقق

| المستوى | المصدر | الاستقلالية | الوسم في التقارير |
|---|---|---|---|
| **Cloud-session evidence** | الوكيل المنفّذ يشغّل الفحوصات في جلسة Claude Code Cloud ويسجّل ما شغّله ونتيجته وSHA الـ commit | **غير مستقل** — الوكيل نفسه كتب التغيير واختبره | `Tested (cloud session)` |
| **Independent CI verification** | GitHub Actions على commit الـ PR | مستقل | `Verified (GitHub CI)` — **غير مستخدم حالياً** (D2 المعدّل)؛ الـ workflows باقية في `.github/workflows/` للاستخدام الاختياري مستقبلاً، دون حذف أو تعطيل |
| **Target environment** | تشغيل فعلي في Railway/Windows/Ubuntu | حسب المنفّذ | `Verified (target environment)` |

لا يُعرض دليل جلسة السحابة أبداً على أنه تحقق CI مستقل.

## 2. الإنتاج — بوابات الجودة الرسمية (Planned، قبل أي go-live)

قبل دخول المنصة الإنتاج (R1.0، M6/M8) تُعرَّف بوابات جودة رسمية في PR مستقل وتُفرض على مرشح الإصدار، وتشمل على الأقل:
اختبارات وظيفية وتكامل، فحص أمني وثغرات (بسياسة حجب يعتمدها المالك)، إمكانية الوصول، الأداء (بأهداف معتمدة — OD-04)، النسخ
والتعافي من الكوارث، وتحقق النشر في البيئة السعودية المعتمدة؛ مع **مراجعة مستقلة** و**اعتمادات المالك والأمن** المطلوبة.
تتابعها [#58](https://github.com/faenazi/ef-ai-workspace/issues/58) وEpic [#36](https://github.com/faenazi/ef-ai-workspace/issues/36).
لا يوجد اعتماد إنتاج حالياً، ولا تُخترع عتبات أو أهداف قبل قرارها.

## 3. ضوابط لا يُعفى منها في أي مرحلة

غياب بوابة جودة رسمية في التطوير **لا** يعفي من: حماية الأسرار (لا أسرار في Git ولا في المحادثات)، البيانات الاصطناعية فقط على
Railway EU West، حظر بيانات الصندوق السرية وبيانات الموظفين، منع ربط Entra الحقيقي، تفويض النطاقات والتعريض العام والإنفاق،
قرارات المخاطر الأمنية، بوابة أمن الحاويات SC-18 أدناه، واعتماد الإنتاج. لا يُحذف أو يُعطّل أي workflow أو فحص أو ضابط أمني.

### بوابة أمن الحاويات (SC-18 — **Approved**، D5 في #16)

لأي عمل يمس الصور أو التعريض العام:

1. فحص الصور الفعلية المثبتة والمشتقة (`scripts/validate/image-scan.sh --include-railway`) عند تغيير أي digest، وأسبوعياً، و**مجدداً قبل أي تعريض عام**؛
   مع تسجيل الأداة وتاريخ قاعدة البيانات والـ digests وكل CVE/GHSA وتقييم الوصول في [vulnerability-register.md](../security/vulnerability-register.md).
2. **لا تعريض عام** (نطاق Railway أو وصول مستخدمين) مع CRITICAL قابلة للوصول أو غير مُقيّمة، إلا بقبول مخاطر **منفصل وصريح لكل ثغرة**
   من المالك (النطاق، الدليل الفني، الضوابط المعوِّضة، المسؤول، تاريخ الانتهاء). تقييم «غير قابل للوصول» من المنفّذ **دليل للمراجعة، لا تفويض**.
3. أي قبول مؤقت يُعتمد لاحقاً ينتهي عند أقرب: إصلاح upstream مدعوم أو 30 يوماً. لا يُخفي الاستثناء نتائج الفحص ولا يعطّل workflow.
4. الفحص في وضع report-only **ليس** نجاحاً أمنياً.

## المسؤوليات والتقارير

- **مالك المنتج:** نطاق الإصدار، المزوّد والحساب، التكلفة، الهوية الرسمية، التوسع، وقرار Go/No-Go لكل R0.x مع المخاطر المتبقية.
- **الهندسة/الوكيل:** PRs صغيرة مراجَعة، تحقق مناسب للمهمة وأدلة صادقة، تراجع جاهز، دقة الحالة في `CURRENT_STATE.md`.
- **الأمن والخصوصية والبنية:** قرار مستقل قبل أي بيانات حقيقية أو tenant Entra أو استضافة سعودية أو إنتاج.
- **أصحاب الأعمال:** مساعدو RFP والتقييم والعقود والمالية؛ مخرجاتها تبقى بمراجعة بشرية.
- فحوصات الأمن (SC-18 أسبوعياً، إزالة طبقة ADR-0012 عند الترقية)، النسخ، حماية `main` والقاعدة الخاصة تستمر **بالتوازي** مع
  R0.2/R0.3؛ الأمان لا يُؤجل إلى R1.0.
- **التقارير:** معايير القبول المقبولة بأدلة مقابل المخططة لكل إصدار، مع Blocked/NOT RUN منفصلة؛ الضوابط عالية الخطر غير المتحققة
  والقرارات المنتهية بمالك وتاريخ؛ رحلة المستخدم المتحققة لكل بوابة (الإصدار، البيئة، SHA). لا ادعاء اكتمال من إغلاق Issues وحده،
  ولا أهداف أداء أو SLA قبل قرار OD-04.
- **حالات مهمة التسليم (Issue):** `Backlog` · `Ready` · `In Progress` · `In Review` · `Blocked` · `Done`؛ `Done` في GitHub ≠
  `Verified (target environment)`.

## 4. السجل التاريخي (محفوظ، غير سارٍ)

بوابة الجودة اليدوية لكل PR (D2 المعدّل، 2026-10-18 → ADR-0011) والاستثناءات المنتهية CI-EX-01..03 محفوظة بنصها في
[docs/history/ci-exceptions-2026-10.md](../history/ci-exceptions-2026-10.md). ما لم يُشغَّل تحت تلك البوابة يبقى NOT RUN ولا يصبح PASS.

## تعريف الجاهزية (Definition of Ready) — قبل بدء Issue

- النتيجة المطلوبة والمخرجات المحددة صريحة؛ المتطلب (FR/NFR) ومعايير القبول قابلة للاختبار ببيانات اصطناعية مسموحة.
- بوابات القرار مغلقة أو الـ Issue موسومة `Blocked`؛ لا افتراض خفي بأن #5 أو #7 معتمدان.
- الاعتماديات والقرارات المفتوحة المؤثرة محلولة أو موثقة كمخاطر؛ مصدر أي تكامل خارجي ومالك تزويد الأسرار واضحان دون أسرار في Git.
- أسلوب التحقق العملي والتراجع وأثر المسارات المراقَبة (ADR-0010) معروفة قبل البدء.
- اعتمادات المالك أو المختصين موجودة للهوية الحساسة أو سير العمل عالي الأثر.
- نطاق الـ PR صغير بما يكفي لمراجعته من الهاتف.
